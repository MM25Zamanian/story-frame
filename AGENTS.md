Repository-wide operating constitution for **StoryFrame** (`story-frame` / استوری فریم — سلسله روایت‌های تصویری و سیر سناریویی تابلوهای دومینو).

Governs authority, architectural truth, documentation consistency gates, engineering independence, Next.js 16/React 19 static export invariants, HeroUI v3 + Tailwind v4 design tokens, Persian RTL geometry, installed skill orchestration, task classification, execution planning, anti-theatrical verification, adversarial UI testing, and independent CTO review.

Detailed framework/subsystem rules → nearest nested `AGENTS.md`, component contracts, or installed skills in `.agents/skills/`.

# 1. Core Operating Principle

Agents are engineering collaborators, not passive command executors.

> Understand the requested outcome, reconcile it with accepted project truth, challenge unsafe, sloppy, or contradictory assumptions, and deliver the smallest correct, verified change.

Agents **MUST** challenge or block when proceeding would:

- contradict canonical project configuration or architecture (`next.config.mjs`, static export, Dockerfile CDN origin);
- violate Persian RTL design integrity, Vazirmatn typographic hierarchy, or the `.shell` (480px) mobile-first viewport;
- introduce generic AI design "slop" (unneeded gradients, neon blobs, heavy drop shadows, pill buttons for cards, fake placeholder stats);
- add unnecessary runtime dependencies, state stores, or server-only abstractions incompatible with static export;
- bypass established component seams, render purity, or named contract conventions;
- compromise image/video media loading performance, blur hashes, or accessibility;
- claim verification that was not empirically executed.

Block only on traceable project rules, unresolved user authority, material invariants, or concrete safety/integrity/aesthetic risk — never on subjective whim.

# 2. Project Truth Model

Three kinds of truth govern this repository. Never conflate them.

## 2.1 Normative Truth (what the system *should* do)

Authority order:

1. Explicit user instructions & active accepted decisions.
2. Canonical product/domain rules:
   - Visual storytelling for Domino storyboards (`data/artworks.ts`, `config/site.ts`).
   - Persian (fa-IR) RTL layout & Vazirmatn typographic hierarchy.
   - Mobile-first `.shell` viewport (centered frame, `max-width: 480px`).
3. Core engineering contracts:
   - Next.js 16 Static Export (`output: "export"`, `trailingSlash: true`).
   - HeroUI v3 (`@heroui/react` 3.2.6) + Tailwind v4 semantic bridge (`styles/globals.css`).
   - Pinned static CDN deployment (`ghcr.io/gecut/nginx/cdn:2.0.0` in `Dockerfile`).
4. Repository-wide policies and applicable skills (`.agents/skills/`).
5. Current implementation.
6. Runtime observation.
7. Inference.

Canonical configuration and specs define intent. Implementation conflicting with them is **drift** unless an accepted decision changed the intent.

## 2.2 Empirical Truth (what the system *currently does*)

Evidence order:

1. Reproducible runtime observation (`next dev`, Chromium/Playwright render, DevTools inspection).
2. Built/shipped export artifacts (`out/` directory, production container).
3. Executable source and configuration files (`package.json`, `next.config.mjs`, `styles/globals.css`, `Dockerfile`).
4. Version-matched official dependency docs (`next/dist/docs/`, `.heroui-docs/react/`).
5. Real browser screenshots, DOM measurements, console logs, network traces.
6. Repository prose and comments.
7. Inference.

Used for debugging, root-cause analysis, layout inspection, and verification. Empirical evidence may prove current code broken; it does **not** rewrite accepted intent.

## 2.3 Structural & Visual Intelligence

- **Structural Intelligence:** Codebase dependency graphs, import trees, caller/callee paths, component composition boundaries, and blast radius.
- **Visual Intelligence:** DevTools measurements (DOM dimensions, contrast ratios, font loading, line wraps), screenshots at target breakpoints (390px, 768px, 1440px), and `break-ui` worst-case data fixtures.

If structural or visual tools disagree with source, verify against source and inspect the rendered browser DOM; treat static assumptions as potentially stale.

# 3. Documentation & Consistency Gate

Every task passes through this gate **before** classification. A user request is a proposed change; it does not automatically supersede accepted truth.

## 3.1 Documented and Compatible
Requested behavior aligns with established domain models (`data/artworks.ts`, site config, semantic design tokens). Proceed using documented conventions.

## 3.2 New but Compatible
Not yet documented, does not contradict. If it introduces **durable** system knowledge (new artwork fields, routing semantics, layout primitives, media pipeline scripts, theme tokens), update its owning data contracts, types, or documentation in the same task. Durable behavior must not live only in source files.

## 3.3 Contradictory — HARD BLOCK
Request contradicts canonical constraints (e.g., requesting server-side dynamic cookies/headers in a static export app, breaking RTL logical properties, replacing the mobile shell without authorization) → **stop implementation**.
1. State the requested behavior.
2. Identify the conflicting constraint or owning config.
3. Explain the material consequence of changing it.
4. Declare implementation blocked.
5. Request explicit user confirmation to supersede.

The original request is not sufficient confirmation. On explicit reconfirmation: task becomes Large, affected configs/docs are updated, and implementation proceeds.

## 3.4 Open Questions — HARD BLOCK
Unresolved ambiguities in artwork metadata, translation copy, or media licensing: identify, explain, block, request user decision. Routine engineering decisions that do not alter domain semantics proceed autonomously.

# 5. StoryFrame System Invariants & Domain Boundaries

Every code change in this repository must obey these foundational technical and aesthetic invariants:

### 5.1 Architecture: Next.js 16 Static Export
- `next.config.mjs` enforces `output: "export"` and `trailingSlash: true`.
- **Zero dynamic server runtimes:** No Node.js runtime APIs at request time, no `next/headers`, `cookies()`, dynamic route handlers, or database servers.
- All routes must be statically exportable (e.g., `generateStaticParams` for dynamic routes like `app/artworks/[slug]/page.tsx`).
- Images use `unoptimized: true` with pre-generated blur data URLs (`npm run images:blur`).

### 5.2 UI Framework: HeroUI v3 + Tailwind CSS v4
- HeroUI v3 (`@heroui/react` 3.2.6) is the component baseline. Refer to the local index in `.heroui-docs/react`.
- Tailwind CSS v4 (`@import "tailwindcss"; @import "@heroui/styles";`) powers styling.
- Semantic Color Palette is bridged via `@theme inline` in `styles/globals.css`:
  - Surfaces: `bg-background`, `bg-surface`, `bg-surface-secondary`, `bg-overlay`.
  - Foreground: `text-foreground`, `text-muted`, `text-accent-foreground`.
  - Accents & Status: `bg-accent`, `text-accent`, `border-border`, `divide-separator`.
- Never hardcode raw hex colors in component classes. Consume semantic tokens.

### 5.3 Layout & Viewport: The Mobile-First Shell
- StoryFrame is an intimate, story-driven artwork showcase.
- Core content is framed within `.shell` (`width: min(480px, calc(100% - 32px)); margin-inline: auto;`).
- Desktop is a centered presentation frame; tablet and mobile scale seamlessly within this boundary.
- Do not break out of `.shell` unless explicitly designing full-viewport lightbox overlays or modal backdrops.

### 5.4 Typography & Direction: Persian RTL
- Direction is strictly `dir="rtl"` with language `fa-IR`.
- Primary font is **Vazirmatn** (`var(--font-vazirmatn)`).
- **Logical CSS properties are mandatory:** Use `margin-inline`, `padding-inline`, `start-*`, `end-*`, `border-inline-*`.
- NEVER use physical left/right (`ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-`) unless specifically required for bidirectional media scrubbers or coordinates.

### 5.5 Motion & Micro-Interactions (Emil Kowalski Standards)
- Library: `motion` (Framer Motion v14).
- Animations must feel responsive and snappy: UI transitions **under 300ms** (typically 150–250ms).
- Easing: Strong `ease-out` (starts fast, feels instant). Never use `ease-in` for interactive UI.
- Buttons & pressable items: subtle feedback `transform: scale(0.97)` on `:active`.
- Entrances: Never animate from `scale(0)` (unnatural). Animate from `scale(0.95)` with `opacity: 0`.
- Modals scale from center; popovers scale from their trigger (`transform-origin`).
- Hardware acceleration: prefer CSS transitions or full `transform` strings over un-accelerated individual properties.
- **Strict `prefers-reduced-motion` compliance:** Always respect reduced-motion media queries.

### 5.6 Production Container: Gecut Nginx CDN
- Multi-stage `Dockerfile`: Node/Bun build stage → `ghcr.io/gecut/nginx/cdn:2.0.0`.
- Static export from `/app/out` copied to `/data/` with `--chown=nginx:nginx`.
- CDN caching headers, immutability, and gzip/brotli delivery are governed by the `nginx-cdn` skill.

# 7. Task Classification

After passing the Gate and inspecting code/dependencies, classify the task as **Small** or **Large**. Coupling, reversibility, and blast radius outweigh raw line count:

### Small Tasks
Bounded impact, localized changes, no changes to shared data contracts or global layout:
- Local UI/styling correction or typography adjustment.
- Copy/metadata updates in `data/artworks.ts`.
- Component-local bug fix or micro-interaction tuneup.
- Adding a single isolated icon or utility.

### Large Tasks
Large when **any** of the following applies:
- Changes to core layout shell (`app/layout.tsx`, `.shell` container, `site-header.tsx`, `site-footer.tsx`).
- Core data schema or artwork type changes (`types/`, `data/artworks.ts`).
- New pages or routes (`app/artworks/...`).
- Media player, lightbox, or video scrubbing engine modifications.
- Upgrades or breaking changes to Next.js, HeroUI, Tailwind, or Motion.
- Dockerfile, build pipeline, or Nginx CDN caching changes.
- Destructive operations (deleting components, refactoring shared tokens).
- Multi-component redesigns or aesthetic overhauls.

# 8. Small Task Lifecycle

```text
Request → Gate → Inspect Code & Tokens → Direct Implementation → Focused Verification → Done
```

1. **Gate:** Confirm compatibility with StoryFrame invariants.
2. **Inspect:** Read relevant component, types, and styles.
3. **Implement:** Make the smallest complete, reviewable change. Obey kebab-case file conventions and semantic tokens.
4. **Verify:**
   - Run typecheck: `npx tsc --noEmit`.
   - Run lint: `npm run lint`.
   - Test UI responsiveness and RTL layout in browser.
5. **Complete:** Confirm deliverable is unabridged.

# 9. Large Task Lifecycle & Execution Artifacts

Large tasks require structured discipline and living artifacts:

```text
Request → Gate → Ground & Frame → Specialist Routing (nexload-reasoning)
  → ExecPlan (implementation_plan.md) → Live Task Tracker (task_tracker.html)
  → Contract Pinning → Phased Execution → Integration
  → Adversarial Stress Test (break-ui) → Verification Gate
  → CTO Review Gate (nexload-cto-review) → Approved? → Done / Repair Loop
```

### 9.1 Living Execution Artifacts

| Artifact | Location | Purpose |
|---|---|---|
| `implementation_plan.md` | Artifact Directory | Authoritative execution model: objectives, constraints, pinned contracts, phased DAG, verification plan. |
| `task_tracker.html` | Artifact Directory | Live visual progress tracker rendered via `<agent-embed>` (Generative UI). Displays phases, %, ETA, active agents, and blockers. |
| `walkthrough.md` | Artifact Directory | Post-execution deliverable: walkthrough of changes, before/after comparisons, and decisive verification evidence. |

### 9.2 Contract Pinning Before Execution
Before authoring code across multiple components or files:
- Pin TypeScript interfaces and props contracts.
- Pin semantic theme tokens and spacing variables.
- Pin data flow and state ownership (Server Component vs Client Component boundary).

# 10. Implementation Discipline

- **Pay Rent:** Every new component, helper, or dependency must measurably pay its complexity rent. Speculative abstractions are forbidden.
- **One Responsibility:** Keep components focused. Extract private helpers locally using `_`-prefixed kebab-case filenames when warranted.
- **Render Purity:** No side effects or DOM mutations during React render. Keep `"use client"` pushed as far down the component tree as possible.
- **RTL & Logical Geometry:** No physical horizontal coordinates. Check flexbox and grid layouts under RTL.
- **Anti-Slop Craft:** No generic AI design templates. Embrace StoryFrame's warm minimalist editorial tone, purposeful whitespace, and precise typography.

---

# 11. Verification Discipline (Anti-Theatrical)

Verification must decisively match the claim. Never claim a check that was not executed.

| Claim | Required Verification Evidence |
|---|---|
| "Types compile" | `npx tsc --noEmit` exits with code 0. |
| "Lint passes" | `npm run lint` exits with code 0. |
| "Build succeeds" | `npm run build` succeeds and produces static export in `out/`. |
| "Responsive & RTL" | Visual inspection at 390px, 768px, and 1440px with DevTools / Playwright; logical properties verified. |
| "Animation feels snappy" | Measured duration < 300ms, ease-out curve, scale(0.97) on press, `prefers-reduced-motion` tested. |
| "Edge cases handled" | `break-ui` adversarial run (long Persian text, empty states, missing media, zoom 200%). |
| "Blur hash works" | `npm run images:blur` succeeds and valid base64 data URLs exist for artworks. |
| "Docker container runs" | Docker build succeeds with static files placed in `/data/` with `nginx:nginx` ownership. |

Lint does not prove runtime layout. Typecheck does not prove visual appeal. Static build does not prove mobile gesture responsiveness. Execute decisive verification.

# 12. Independent CTO Review Gate

Every Large Task requires an independent architectural review before completion using `nexload-cto-review`.

The review evaluates:
1. **Requirement Fidelity:** Does it solve the exact problem without scope creep?
2. **Engineering Integrity:** Are React 19 purity, state ownership, and static export limits respected?
3. **Visual & Design Craft:** Does it maintain StoryFrame's editorial standards, RTL correctness, and zero-slop rule?
4. **Complexity Cost:** Did every new abstraction pay rent?
5. **Verification Freshness:** Was decisive, claim-matched verification executed?

**Verdicts:**
- `Approved`: Flawless or completely sound execution.
- `Approved with minor issues`: Trivial non-blocking comments.
- `Needs revision`: Actionable defects; task enters Repair Loop.
- `Blocked` / `Rejected`: Structural or invariant violation.

# 13. Anti-Patterns Catalog

| Anti-Pattern | Definition & Prohibition |
|---|---|
| **Blind Obedience** | Implementing a request that breaks static export, RTL, or mobile shell without surfacing the conflict. |
| **AI Slop & Generic Tropes** | Adding unnecessary gradients, glowing borders, card pill shapes, or cheesy marketing copy. |
| **Physical CSS in RTL** | Using `ml-`, `mr-`, `pl-`, `pr-`, `left-`, `right-` instead of logical `ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`. |
| **Dynamic Server Illusion** | Introducing server-only cookies, headers, or runtime DB calls into a Next.js `output: "export"` project. |
| **Placeholder Code** | Leaving `// TODO`, `// ...`, or partial implementations (violates `full-output-enforcement`). |
| **Verification Theater** | Claiming code works merely because ESLint or TypeScript exited 0 without testing rendered UI. |
| **Progress Theater** | Fabricating ETA or % completion on tracker without real phase transitions. |
| **Animation Bloat** | Putting slow (>300ms) or `ease-in` animations on frequently used buttons or keyboard interactions. |
| **Over-Routing** | Invoking all 6 reasoning specialists sequentially for a simple single-file change. |
